## Minimal interface the tests import (the report fixes semantics, not names; one adaptation point each at the top of the test file)
Module `src.orchestrator.decision_memory` (env `P9_MODULE` redirects the tests if the worker picks another path, e.g. `src.utils.*`):
- `question_key(question: Mapping) -> str`: hex digest (>=16 hex chars) of the JSON-able question; pure function of content.
- `DecisionMemory(path)`: file-backed store; `path` = str|Path, location is the constructor argument only.
  - `.lookup(question) -> decision | None`: `None` == miss; a **hit increments `.applied_count`**. Falsy decisions (`False`, `0`, `""`, `{}`) are hits.
  - `.record(question, decision) -> None`: durable on return (a new `DecisionMemory(path)` sees it); last write wins; accumulates with earlier runs.
  - `.applied_count: int`: hits since this instance was created (one instance == one run). This is the "count reported"; where it is surfaced is the hook's job.
- Not specified / not tested: concurrency (report's own Ceiling), tuple-vs-list equivalence, entity-pair order symmetry, revocation (Deferred).

## For the lead's gate-hook acceptance (NOT tested yet; HITL resume trap §2.6)
`interrupt_before` means the gate node's body never runs on resume, only the router does, so a lookup placed inside `human_review_*` after the interrupt is dead code on resume,
and a lookup that decides "skip the gate" must happen where it still runs. To check once the hook exists:
1. **Pre-interrupt placement.** Auto-apply happens in the producing node or the router (code that does run on resume), never only in the gate body. Test by driving the real graph
   with a checkpointer: run 2 with all questions remembered must not pause at that gate at all (no `__interrupt__`), and the gate's decision state equals run 1's.
2. **Partial hit.** Remembered + new questions in one gate: only the new ones are in the interrupt payload; after `update_state(as_node=gate)` resume, the remembered decisions are still in state (not lost
   because the gate body did not run) and the new answers are recorded **at resume time** (the recorder must be on a path that runs on resume, i.e. the router/producer, not the gate body).
3. **Count surfaced.** `applied_count` reaches the run status / UI payload (`get_workflow_status`) for each gate; zero when none matched; a `completed` status alone is not evidence (CLAUDE.md).
4. **Key inputs exclude volatile fields.** The question handed to `question_key` contains only entity pair / proposed structure / field mapping, not thread id, run id, timestamps, row counts or
   scores that vary run to run; two runs over the same data produce the same keys (run the pipeline twice end to end and compare the key sets).
5. **Rejected/edited decisions** recorded as the human's final answer (edited mapping, not the proposal); an abandoned or errored gate records nothing.
6. **Failure isolation.** Unreadable file at gate time -> gate still pauses and asks; a failing write never fails the run.
7. **Autonomy / D-09.** Memory applied only inside the configured autonomy mode; recorded decisions carry no model-written text as authority.
8. `handle_error` / error gates are not memoised (a past "retry" must not replay).
9. §2.4 grep and arch-lint on `human_nodes.py` / `graph.py` diffs; no new module-level state in `src/mcp_server/tools/`.
10. Live (unverified here): two real runs on the pagila/enrichment corpus, second asks zero at each gate, with direct inspection of the file.
