## Why REJECT: the shared-part rule trades false flags for MISSED over-merges, and adds new false flags
All numbers: 3 seeds / 200 clusters unless stated; "base" = 893da8f.
1. **Two different people sharing only a surname (family, common surname) are no longer flagged: 0/20, base 20/20** (`test_planted_sharing_only_the_surname_still_flagged`). Sharing only a given name was already missed at base (0/20 both) -- pinned as a control, not a regression. The report's Verify shape (both parts different) hides this; for a flag whose job is to catch over-merges, "Jane Smith + John Smith" is the commonest real over-merge. Bigger chains (k=3,5,8 people, 30 % one given name, 30 surnames) stay flagged (>=57/60), so chaining is not the issue; the single-pair case is.
2. **Organisations: any second column whose name contains the best column's hint ('name') is folded in** (`contact_name`, `parent_name`, `country_name`, `username`, `filename`, `street_name`...). Two different companies sharing that value (same contact, same parent group, same country) are one group: planted fusions 0/20 flagged, base 20/20 (`test_org_planted_fusion_sharing_a_second_name_column_is_still_flagged`, all three columns). Person+`street_name`(5 values): planted caught 7-11/20, base 20/20. Distinct-per-company values (control) are fine, and a single name column is unchanged -- but the project's data is organisations, and "same country" / "same parent" is a normal property of an over-merge.
3. **New false flags vs base on true clusters when one origin keys the name differently** (mixed schema; only multi-part names contribute parts, so a fused or reordered single-column name has nothing to link by): `full_name="surname, given"` or `given_name="surname given"`+NULL surname 58-70/200 (base 0); same + typo 165-172/200 (base 0); initial + typo'd surname 28-35/200 (base 0); typo'd given + NULL surname 198-200/200 (base 0-1). Also column order still matters when BOTH origins differ in order and a fused-name origin exists: 8-11/200 false flags (base 48-125; strictly better, not fixed). One origin reordered alone changes nothing (control).
4. Same-given-and-typo family beyond c8: the live sample's one residual (c8: given missing AND surname substituted) is a compound corruption at ~1/30; expect a residual of order 2-3 % of Febrl4 pairs (~100+ of 4,989), not "~0". Judgement on the xfail: **keep `test_p16_true_person_pairs_are_not_flagged` strict-xfail** -- no name token or part survives in c8, and a rule that cleared it would be clearing it by overfitting to the one pair; the report's "≈ 0" should be read as "~2-3 %", down from 17.8 %.

## Suggested direction (worker's call)
Link on a shared part only when the NON-shared parts are compatible (missing, or within the run-derived threshold of each other after allowing a swap), instead of unconditionally; and let a single-part name contribute its own tokens as parts so a fused/reordered origin links by token. Restrict folding to columns that are siblings of the best column (same prefix/suffix pattern is a hint-free proxy), or at least exclude columns whose values repeat across many records (a run-derived, not fitted, cut such as "value held by more than one cluster's records").
