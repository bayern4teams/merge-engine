## Findings, ranked (xfail tag in brackets)
1. HIGH [F5, F5b] "Confirmed at the gate" is unreachable. `api.Feedback` has no `thresholds` field (pydantic drops it; verified: the dict reaching
   `resume_workflow` is `{approved, decision, node}`), and the frontend never mentions `pre_load_gate` (nor `destination_defects`). Through the API/UI
   the operator neither sees `would_fail` nor can edit; every default refusal is a dead run (disposition "fail" -> END) that must be re-run from
   extraction. Only in-process callers can use the edit path. Reported, not fixed (per brief).
2. HIGH [F1] Coverage is not measured for an entity with records but no `field_mappings` entry AND no `unmapped_fields` entry (map_fields only
   records fields it processed; an entity the mapper never reached has neither). Measured: half the entities unmapped-and-unlisted -> would_fail False
   (min coverage 0.667); a run where NOTHING mapped and nothing is listed -> would_fail False. That is the report's own "zero mappings for 8 of 16".
3. HIGH [F2] NULL identity: a record counts as non-NULL if ANY key containing a `_NAME_FIELD_HINTS` substring is populated (`company`, `org`,
   `label`, `title`, `email`...). 78 of 100 NULL `name` with a populated `company_id` / `organization_type` / `label` / `email_verified` -> not flagged
   (measured 0.025). The old incident (78/99 NULL `company.name`) escapes whenever the table has a sibling id/type column matching a hint.
4. MEDIUM-HIGH [F3] False refusals on size skew. Measures are shares of the entity and the floor is "one record of the MEDIAN entity", so a small
   healthy entity trips: six 500-row entities + a 50-row lookup (clusters <= 3, no NULLs) -> refused on largest_cluster (0.041 > 0.008); the same lookup
   with ONE NULL name -> refused on null_identity (0.02 > 0.002). 200-row lookup + 1 NULL still refused; 2000 rows passes. Lookup/junction tables
   beside big entities are the normal shape of the corpus. Combined with finding 1 the operator cannot recover.
5. MEDIUM [F4] Disguised constants (plan 2.4): `2 x median` and the `1/2` cap and `1/(2*widest)` are policy numbers, not counts of the corpus. They are
   the effective rule exactly where it matters: 45% NULL names in EVERY entity, or a 45% cluster in EVERY entity, passes (60% fails only because it
   crosses the cap). The ponytail comment admits "all bad alike is caught only by the floors". The static grep passes only because 2 and 1/2 are in
   the allowed unit set; lead decides whether a majority cut is an acceptable standing constant (name it in the spec like the 0.95/0.70 band) or the
   rule must be derived. NOT a cut I would call fitted to the corpus; it is a hand-set multiplier.
6. MEDIUM [F7] Resume trap, second leg: the confirmed thresholds live only in `human_feedback`. A load that fails into the error gate and is
   retried replaces `human_feedback` with the error gate's feedback, `_confirmed_thresholds` returns None, and the retry is refused by the proposals
   the operator had overridden ("fail" -> dead). Verified end to end with the real graph and manager. Fix: copy the confirmed numbers into a state key
   at resume, or persist them in `pre_load_gate`'s own output on the first evaluation.
7. MEDIUM, cost (not xfail): `pre_load_gate` costs as much as `build_reconciliation_report` (each loads every extracted record and runs
   quality_signals): 100k records 4.6 s, 300k spooled 17.9 s EACH, linear, 570 MB RSS. Per run it executes 4 times (gate preview: report + gate; load:
   gate + report) ~ 72 s at 300k, ~20 min at ~5M. Gate fetch is once per pause (rehydrate only otherwise). Compute once at the gate and carry numbers.
8. LOW/judgement (1 of the brief) One zero-mapped, unmapped-LISTED entity among healthy ones refuses the whole run. Measured: P17 fixtures with the

9. LOW: unknown invariant names in the edit (`null_identity` typo) are ignored silently (`unusable_edits` only covers known names with bad values);
