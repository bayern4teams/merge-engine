## 2. r2's new mechanisms: findings, ranked (xfail tag in brackets)
1. MEDIUM-HIGH [test_a_tiny_lookup_does_not_hide_a_giant_cluster_in_another_entity; ..._null_burst_...] **Small-entity slack is global, so one tiny entity blinds the
   invariant for the whole run.** Ceiling = max(2 x median, slack of the SMALLEST entity), cap 1/2. Measured (7 x 500-row entities + one lookup; one 500-row entity has a
   225-record single cluster = 0.449 share): lookup 500/200/50 rows -> threshold 0.010/0.025/0.102 refused; 20 rows -> 0.263 (0.25 giant would pass); **10/5/3/2 rows -> 0.5, a 45% giant
   cluster PASSES**. NULL burst (225 of 500 names NULL = 0.45): 500/50/10/5/3 rows -> thr 0.002/0.02/0.10/0.20/0.333 refused; **2-row lookup -> thr 0.5, PASSES** (1 row too;
   a 3-row lookup lets a 33% NULL burst through). r1 caught both (it only false-refused small lookups, finding 4). The r1->r2 trade moved the hole to exactly the incident's shape
   (a giant/NULL entity beside lookups, which the report calls the normal corpus shape). Not F4's uniform-badness ceiling: ONE entity is bad and the others are healthy.
   Fix shape: allow each entity its OWN slack (violated if share > max(2 x median, 1/own_size) for that entity), not the run-wide minimum.
2. MEDIUM [test_a_healthy_mixed_origin_entity_is_not_a_null_identity_failure] **One identity column over the union of keys miscounts two-origin entities.** Records of an origin that
   names the concept differently (`company_name` vs `org_title`: the repo's own comments at resolve_entities `_best_name_field` and load_data's coalesce) are counted NULL on the picked
   column. 100 records, EVERY name populated: 20% from the second origin -> measured 0.20 NULL (threshold 0.02-0.01: refused); 50/50 -> 0.50. When all entities are mixed-origin it
   passes only because the shape is uniform. r1 (any hint column) handled this; this is a regression from the r2 fix for F2.
3. MEDIUM [test_a_fully_mapped_entity_with_audit_columns_is_not_a_coverage_failure] **Coverage width = max(listed, carried) over-counts columns the mapper legitimately ignores.**
   map_fields_node builds the schema without `_` columns and without P12 `metadata_only` columns (they stay in the records, are in neither `field_mappings` nor `unmapped_fields`).
   4 of 4 business fields mapped + k audit columns (created_at, updated_at, deleted_at, etl_batch_id, row_hash, source_system...): k=2 -> 0.667, k=4 -> 0.500 (passes at equality),
   **k=5+ below the 0.5 floor with peers at 1.0; k=8 -> 0.333, refused** although coverage of business fields is 100%. Lookup/junction tables (id, name + 5-8 audit columns) are the
   at-risk shape. Also the mapper samples only the first 500 records, so a field first appearing later inflates the width the same way.
4. MEDIUM-LOW [test_an_id_column_does_not_hide_a_null_label] **"id-like last" is only the second sort key, after hint rank.** `company_id` (rank 4) beats `label` (7) / `email` (8):

5. MEDIUM-LOW [test_a_sparse_optional_nickname_does_not_make_a_person_table_a_null_identity_failure] Same rule, other direction: `nickname` (8) beats `first_name`/`last_name`/`full_name`;
