## Changes
1. Direction documented in place (comments in _apply_rule "priority" branch, impl docstring and the origin_priorities build): higher priority number wins, do not reverse. No behaviour change.
2. Priority keyed by (origin, field): origin dict key `field_priorities: {field: int}`; stored as (origin, field) keys in the same origin_priorities dict, lookup falls back to origin-level value then 0. Exact field-name match (no globbing). Acceptance test key name "field_priorities" is already in PRIORITY_ENCODINGS; no adaptation constants edited.
   measured_reliability: chose USED, not removed. Reason: the rule is NOT dead in the orchestrator path (unify_entities passes a table; with tied priorities it decides - test_2e). The report's "dead whenever priority is set" is half right; what was truly dead is the handler/impl path with no table. Minimal fix: when field_reliability is None, impl measures it from the cluster's own records (measure_field_reliability). Removal would have changed saved configs that name the rule. Ceiling: a single cluster is a small sample; only evidence on that path.
3. Option A: `completeness` renamed `longest`, alias dict _RULE_ALIASES applied in resolve_policy (old configs/profiles load, same meaning on text). Why A over B (record-level fewest-NULLs): the report allows either; A needs no record-level machinery and cannot change stored configs' winners on text. `longest` is text-only: if any candidate value is non-str it is a no-op and the chain moves on (so 9.5 vs 10 no longer ranked by digit count). Behavioural consequence: numeric fields without a numeric rule (e.g. default chain priority,longest,recency) now fall to recency instead of digit-length. winning_rule is now recorded as "longest" (was "completeness"); DEFAULT_POLICY and description/summary/*_notes defaults renamed. `shortest` unchanged.
4. first_seen is a total order: min over (origin, _origin_table, _origin_id_row) as strings; the final chain-exhausted fallthrough uses the same rule instead of candidates[0]. _origin_table added as a middle key beyond the report's "origin ASC, source id ASC" because the record id used elsewhere is origin:table:row and row ids alone can collide across tables.
5. numeric_max/min conflicts still resolve to the max/min, and the conflict record gains `numeric_disagreement: {min, max, spread, relative_spread}` computed on parsed numbers (money strings handled via _numeric_value). No threshold. build_reconciliation_report adds entity key `numeric_disagreements: {field: {clusters, max_spread, max_relative_spread}}` only when any exist. NOT added as a red flag: that would downgrade the grade on every normal multi-source revenue disagreement; leaving that call to the lead / P10.
