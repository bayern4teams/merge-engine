## Finding about the premise
The report's "serially" is stale. `map_fields_node.py` (Phase 2, "Part 1.5 B.1") already runs the calls through an **unbounded**
`asyncio.gather(..., return_exceptions=True)` and merges in `target_entities` order. The live defect is the missing bound
(16 entities => 16 simultaneous LLM calls against an endpoint whose ceiling the report says is the real limit). So tests 1, 2, 4 are
regression guards that already pass; the negatives are the bound tests.

## 2.4 no fitted constants (6a-6d), baseline today 2026-10-04
- Corpus-literal grep (`France US SAS Berhad Global Group Holdings companyname main_entity_id company_relation staff`, word-bounded) over
  `map_fields_node.py`: **0 hits**. Test 6a fails on any.
- Module numeric constants today: `_MAX_SAMPLE_RECORDS = 500`, `_MAX_SAMPLE_VALUES = 10` (pre-existing, not P11; pinned).
  The existing pattern: `resolve_entities._LLM_CONCURRENCY = 4` (module constant, `asyncio.Semaphore(_LLM_CONCURRENCY)` built inside the function,
  also `_LLM_CHUNK_SIZE = 40`, `_MAX_LLM_PAIRS = 200`; not touched). 6b: P11 may add at most one new numeric name and its value must equal
  `_LLM_CONCURRENCY` (re-import or equal); any other new number fails. 6c: no inline numeric argument to Semaphore/Executor/Pool/Limiter/Queue.
  6d: no new module-level mutable/semaphore state (plan 2.5; a shared loop-bound semaphore also breaks 3d).
- "Would a count over the corpus produce this?" The 4 is not a count; it is the endpoint-concurrency ceiling the report names, and is sanctioned only
  as the SAME constant already used by resolve_entities. A new, different number (e.g. 8, 16) is a REJECT unless the spec names it.

## Adaptation points / interpretation calls (top of the test file)
- Bound is read from any int in the node named `*CONCURR*|POOL|WORKERS|PARALLEL|SEMAPHORE`, else `_LLM_CONCURRENCY`. If the pool lives in a shared helper,
  3b skips and the other tests still bind to `_LLM_CONCURRENCY`.
- `map_fields_impl` is patched on the node module by name (it is imported there today); retarget `STUB_TARGETS` if moved.
- Order: for all-LLM entities, key/list order must equal `target_entities`. With skipped (no-field) entities only timing-independence is asserted, because today's
  merge already writes those first (not literally serial-interleaved); not treated as a defect.
