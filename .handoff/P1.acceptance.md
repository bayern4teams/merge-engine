## The one API contract imposed
`_tokenize_field(name, vocabulary=None) -> list[str]`; `vocabulary` = iterable of lowercase words observed in
the destination schema at runtime. One-argument call and empty/None vocabulary behave exactly as today.
Everything else (how `map_fields_impl` builds the vocabulary, where the ambiguity report lives) is free.

## What is checked (acceptance item -> tests)
1. 4 missed fields map (`foundingdate`->founded_date, `taxregistration`->tax_registration_number,
   `contactemail`->primary_contact_email, `postalcode`->mailing_postal_code); the 7 already-mapping do not regress;
   3 planted negatives (`legacyflag`, `colorcode`, `presspoint`) stay unmapped with the old reason; camel/snake controls unchanged.
   Plus a second, unrelated destination (vehicle_*; no corpus literal): concatenated names must map exactly as their camelCase
   twins (5 map; `wheelbase`, `zzqxv` do not). A no-op fix fails both.
2. Tokeniser: `companyname`->[company,name], `businessaddress`->[business,address] with those words in the vocabulary;
   vocabulary lacking `business` -> `businessaddress` NOT split; partial coverage -> no partial split; invented words
   (`zorbquix` with vocab {zorb,quix,flim}) split - impossible for any built-in dictionary.
3. Snapshot: 22 camel/delimited names (snake, kebab, dotted, spaces, digits, `__id__`, `ISO3166Code`, empty) equal today's
   `_tokenize_field` output, with no vocabulary AND with a vocabulary of their own pieces. (All-caps runs such as
   `HTTPServer`/`CEOName` are deliberately excluded: today's output `httpserver` is arguably a bug, not a contract.)
4. Ambiguity: vocab {bar,ton,bart,on}; `barton` = bar|ton or bart|on. Must not be mapped, and the result (anything outside
   `field_mapping`) must contain an entry mentioning `barton` whose serialisation contains "ambig" (any key/shape: a
   `reason`, a new `ambiguous_splits` key, an extra key on the unmapped entry). The tokeniser itself must not return either
   split. Merely-unmatched names (`presspoint`, `zzqxv`...) must NOT get an ambiguity entry.
5. Reason string for unsplittable names stays exactly
   `"No matching destination column found; destination schema is authoritative"`; `schema_changes == []`.
6. Grep/AST (plan 2.4): zero hits in map_fields.py for `France|US|SAS|Berhad|Global|Group|Holdings|companyname|
   main_entity_id|company_relation|staff|zoominfo` (baseline today: 0). No new hard-coded word list: today there are 7
   literals of >=3 strings (lines 875 `_SAFE_COALESCE_QUALIFIERS`, 909 `_ROLE_QUALIFIER_PREFIXES`, 957-961 synonym lists);
   count must stay <= 7 and no function named *token*/*split*/*segment*/*vocab* may contain one.
   Numeric constants: reviewer asks "would a count over the corpus produce this?" (none is expected).

## Satisfiability / traps found while deriving
A throwaway prototype (scratchpad, not in repo: vocabulary-aware min-segment split + ambiguity tag) passes 63/63, so the
tests are satisfiable. Trap: `foundingdate` needs INFLECTION-aware segmentation - the destination vocabulary holds `founded`,
not `founding`; a plain exact-word split leaves it unmapped (my first prototype failed exactly there). Use `_stem`-style
equivalence when matching segments, not a longer word list.
