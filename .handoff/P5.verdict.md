## REJECT reasons (reproduced, scripts above)
1. **Realistic multi-field corpora raise `CandidatePairBudgetExceeded` where the old code ran.** Company corpus,
   2,200 records (name, address, city, state, zip, phone, email, website, tax id): new RAISES (bound 12.97M
   > guard 5M; only 2.4M distinct pairs exist); old: PC 0.990, RR 0.9954, 11k pairs, 3.3 s. Same with
   name+address+city+email only (7.8M). Persons 7,200 with an email column or a dob column: new raises.
   Cause: structural tokens (`com`, `www`, `https`, `1` from `+1-`, `street`, `info`) form ~6 near-equal
   blocks of ~2,100 members. P2 purging (a block must exceed every smaller block combined) purges NONE of a
   tie/near-tie, and the guard sums comparisons per block with multiplicity (a pair sharing 50 tokens is
   counted 50 times), so it fires on a bound far above real memory. Meta-blocking (the "mandatory" stage) never
   gets to run. Boolean column alone (2 blocks of ~1,500): 2.25M pairs, nothing purged.
2. **Guard lifted, it is unusable anyway:** same 2.2k corpus, still running after >3 min (Python loops over
   ~19M multiplicity comparisons x 2 passes). Passing cases are slow: 2.2k name+city+email 8.5 s; 7.2k
   names-only 27.6 s / 234 MB for 98k candidates (lead reports 6.1 -> 1.9 s on a names-only 6,400 corpus: true,
   but that corpus has no structural tokens). 22.5k names-only: raises (10.1M). So the "practical ceiling" is
   ~5-10k records on token-rich schemas, not the 20-50k asked about; OOM guard fires on realistic data.
3. **Non-Latin text is invisible.** `_tokenize` is `[a-z0-9]+`: `Muller`/`Mueller` fine, but `Müller` ->
   `m`,`ller`; CJK/Cyrillic/Arabic values yield no key. Records whose only content is non-Latin share the
   all-pairs fallback block; mixed records silently lose those fields. 3,000 CJK-name records: 0 candidates
   (id tokens only), old: 4.5M (all-pairs). Silent recall loss, no stat. Pre-existing tokenizer, but P5 makes
   it the sole key.
## Minor
- Row-id/PK columns are data values: `id` `1..N` in two origins co-block same-numbered rows (junk pairs).
- Nested dict values: `str()` leaks the nested KEYS as tokens (`{'k':..}` -> `k`): small breach of "names never read".
- Explicit `blocking_keys` naming a nonexistent field: every record falls in `__nokey__` -> all pairs (old behaved alike).
- Phonetic loss: confirmed real (typo'd surname + nothing else shared -> no pair); documented by worker (ponytail note).
  Planted-dup PC stays 0.98-1.0 only when another field is shared. Cost accepted by report; not a reject cause.
- `www.x.com/careers` vs `x.com`: share `x` and `com`; `www/https/com` become the universal blocks of reason 1.
- CEP/CNP omission: NOT a plan violation on its own (plan lists "WNP / CEP / CNP" as alternatives; report table
  shows them as alternatives; WNP is implemented). Block filtering omitted as a fitted `r`: defensible
  (report says "r as a ratio" but plan §2.4 forbids fitted). BUT the missing cleaning is exactly what reason 1 needs:
  a per-record cap computed from block volume (CNP `k = sum|b| / |E|`) or purging that handles tied dominant
  blocks would bound the work before materialisation. Recommend: make purging tie-safe, count DISTINCT pairs in
  the guard (or run WNP incrementally per node), re-run my company corpus (gen.py 2000 1) as an acceptance case.

REJECT cause: **recall regression on typo'd person pairs, much larger than the lead's 296 -> 283.**
Corpus (pers2.py: 6,400 base + 400 dups with one typo in the surname; shared first name + city + unique id):
| shape | old 9d8c392 PC | new PC | cand old/new |
| full_name + city | 386/400 (0.965) | 209/400 (0.522) | 63.9k / 18.1k |
| first_name + surname + city | 314/400 (0.785) | 209/400 (0.522) | 28.4k / 18.1k |
Names+city only (old cannot run: guard): new PC 0.19 at 7.2k, 0.056 at 22.5k; dob column: 0.24 / 0.025.
Mechanism (checked on lost pairs): the filter is per record and asymmetric. Original B's surname is shared by one other
person (block size 2), so B's geometric mean drops its first-name block (size ~26); the dup keeps first-name (26) and
drops city (207); the typo'd surname is a singleton. B and the dup then share no retained block. A common surname
shared by two people is routine, so this is not exotic. Recall now falls as N grows (0.19 -> 0.056).
Report PC 0.96-0.99 is not met on person-type duplicates; floors in the acceptance tests only cover planted dups
with several shared fields.

Geometric-mean rule, fitted? No numeric constant (grep clean; only 0/1/2 literals; N/2 purge = IDF<1 bit, parameter-free).
But the choice of mean (geometric over arithmetic) was selected by measurement on the company corpus (code comment says
so), so it is a tuned design choice, not derived; defensible only with that disclosure. Block filtering is lossy
by design in the literature too; the fix must keep a pair when EITHER side keeps the shared block (union rule), as WNP
already does, or filter against the block, not each member's own mean.
