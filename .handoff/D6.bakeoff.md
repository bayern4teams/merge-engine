# D6 bake-off — pre-registered rule (written BEFORE the arm ran, 2026-11-26)

Hypothesis (HANDOFF Phase 6b item 4, verbatim): product codes like
"DP-29F" vs "DP29F" score low. Candidate: strip separators inside
alphanumeric tokens before comparing (reuse PRE-D2's separator removal).

Mechanism read first (no code change yet): PRE-D2's `_conflicting_codes`
already compares whole names with separators removed (`_WORD_RE` join), so
"DP-29F" finds "dp29f" there. But `_tokenize` splits ON separators
(`[a-z0-9]+` runs), so at token level "dp-29f" is tokens {dp, 29f} vs
{dp29f} — the prefix rule needs len>=3 on both sides and the typo rule
cannot bridge a 2-vs-5 length gap, so the code token contributes little to
`token_sim`. That is exactly the hypothesized hole.

## Rule (from the HANDOFF — pre-registered before the arm ran)

Measure on abt_buy (in-process, LLM off, same harness as D1/D5 bake-offs):
- recall@0.70 >= main - 0.01
- precision at 0.95 not lower than main
(the HANDOFF names `score_probe abt_buy`; score_probe needs an app-run spool
+ `benchmarks/truth/*.json`, unavailable in this environment — deviation:
measured with the in-process bake-off scorer on identical records/candidate
pool; the two metrics are the same quantities.)
If it does not help, leave D6 open and say so. No implementation until the
arm passes.

## Arm (the candidate, harness-side swap, no src/ edit)

D6-sep: token sets are built, then hyphen/underscore/period-adjacent token
runs are joined before comparison — i.e. separators inside alphanumeric
tokens are stripped, PRE-D2's exact separator set, reused not redefined
(the bake-off imports PRE-D2's `_WORD_RE` / strip shape). IDF weights are
recomputed on the transformed tokens (same corpus statistics path as arm A)
so nothing else about scoring changes.

## Results

Measured 2026-11-26 (`d6_check.py`, abt_buy 2,173 records, in-process,
LLM off, identical records/candidate pool; scored = 33,740 vs 33,755 —
blocking barely moved):

| arm | P@0.95 | R@0.95 | F1@0.95 | R@0.70 | over-merged | wall_s |
|---|---|---|---|---|---|---|
| main (tree tokenizer) | 0.0346 | 0.0107 | 0.0164 | 0.0429 | 119 | 11.2 |
| D6_strip | 0.0448 | 0.0143 | 0.0217 | 0.0555 | 121 | 10.3 |

Rule: recall@0.70 +0.0126 (target >= main − 0.01: PASS with margin),
precision at 0.95 +0.0102 (not lower: PASS). over-merged +2 — within the
D-series tolerance shape. **D6 helps; implement.** (Honest scope note: the
floor is the same low one D1 measured — this is a real lift on the metric
the HANDOFF named, not a suite-fixing win; the mid-band + I-5 mechanisms
still dominate this suite.)

## Implementation deviation (recorded; final in-tree rule)

The first implementation (strip `[-_.]`) was caught by
`test_p14_acceptance::test_2` — the snapshot's own docstring names this
exact failure mode ("a text-grain change that tokenises 'user1@mail.test'
would inflate 'mail'/'test'"): stripping `.` joins email/domain fragments
into mega-tokens and moves the fitted prior. The dot is NOT PRE-D2's
separator family anyway — `_conflicting_codes` uses `_WORD_RE` (`[^\W_]+`),
whose removal set is exactly `[-_]`. Second iteration (strip `[-_]` between
alphanumerics) then moved the SAME snapshot for a second named reason:
phone "555-1000+k" is digit-digit, and joining it re-tokenizes phone values
that flow into the fitted model. Final in-tree rule: strip `[-_]` when at
least one side of the separator is a LETTER (code spelling "DP-29F",
"PS-LX350H"); pure-digit runs ("555-1000") keep their tokens. Re-measured
on abt_buy (same harness):

| arm | P@0.95 | R@0.95 | F1@0.95 | R@0.70 | over-merged |
|---|---|---|---|---|---|
| main (tree tokenizer, pre-D6) | 0.0346 | 0.0107 | 0.0164 | 0.0429 | 119 |
| D6 final (letter-side rule, in tree) | 0.0482 | 0.0143 | 0.0221 | 0.0537 | 118 |

Rule passes: recall@0.70 +0.0108 (>= main − 0.01), precision +0.0136,
over-merged −1 (no increase). P14 atomic snapshot untouched by design;
D6 unit tests pin the tokenizer contract (join codes, keep phone format,
keep email splits, `dp--29f` is not a run join).
