## Is the new total the same thing as `band_summary.predicted_counts.possible`?
Yes. `_pending_merge_candidates` and `_band_fields` read the same `scored_pairs` with the same test
(`auto_exclude <= conf < auto_match`); the former then sorts and slices to the cap. They differ only on a NaN
score, which neither counts. So the total can be derived at the gate from `band_summary` or stored next to the
list; d1 pins them equal. Caveat: after `apply_band_decisions`, `band_summary` is not updated while
`pending_merge_candidates` shrinks (f2): "47 of 80" (band size of the run) is accepted, "47 of 12" is not.

## Calibration (for attack mode)
* Satisfiability: a throwaway monkeypatch of `_build_matches_interrupt` (not in src; deleted) adding a per-entity
  `{listed, total}` block, an overall one and "N of M" in the note passes all 36. So the file is not unsatisfiable.
* Hazard not testable here: `resolve_cache` keys on inputs and `_CACHE_FORMAT_VERSION` (=1). If the fix stores a new
  field in the `resolve_entities_impl` result, a cache entry written by the pre-fix code is served without it on the
  same data. The fix must bump the format version or derive the total at the gate; attack mode should read the diff
  for that.
* Not covered: paging UI (the report offers paging OR "N of M"; these checks accept either as long as the first page is
  strongest-first and the total is stated); a browser render of the text (static grep only); live Abt-Buy (1,330 /
  50) needs the Leipzig data: "implemented, unverified" until run locally.
* A fix that raises the cap to hide the gap is caught by c1/g1 (cap constant and no new numbers).
* Constants used (0.70/0.95 band edges, 0.0005 rounding tolerance) are the report's band table or test tolerances.
