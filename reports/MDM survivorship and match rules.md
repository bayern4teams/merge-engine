# Mature MDM platforms derive constants, not hardcode them

The single most transferable finding across Reltio, Profisee, Data Ladder and the entity-resolution literature is architectural, not algorithmic: **survivorship in a mature platform is a read-time projection over retained provenance, never a destructive write**, and **every general rule mechanism replaces a human's guess about which tokens, sources or keys matter with a count taken over the corpus at runtime**. Reltio ships twelve named `survivorshipStrategy` values composed as a *narrowing* fallback pipeline — each step filters the previous step's winners, gated by an explicit `fallbackUsingCriteria` trigger — and computes the operational value (OV) per read, per role, so losing values remain queryable and unmerge stays possible ([Survivorship Rules](https://docs.reltio.com/en/model/consolidate-data/design-survivorship-rules/survivorship-rules)). A field present in only one source is handled by an explicit short-circuit that **bypasses source priority entirely**; a contested field runs the strategy; and several source fields meaning one thing are resolved *upstream* of survivorship as a mapping problem, which both vendors keep architecturally separate ([Data Ladder, Source-to-Target Mapping](https://dataladder.com/source-to-target-mapping-best-practices/)). For the audit question — whether four proposed fixes generalise or are fitted to one PostgreSQL source pair — the literature supplies a mechanical test that needs no new data: a general mechanism's constants are computed from the data (`log(N/count(token))`, discriminability × coverage, co-occurrence weights, inclusion dependencies over column values); a fitted one contains literals drawn from the corpus (a suffix list, a table name, a tuned threshold). The uncomfortable corollary, documented explicitly, is that **a hand-picked blocking key with high candidate precision is itself evidence of fitting**: the general schema-agnostic baseline achieves >90% recall at precision **below 0.003** ([Generalized Supervised Meta-blocking](https://arxiv.org/html/2204.08801)), so a key that returns few, mostly-correct candidates was almost certainly chosen with knowledge of the answers.

## Twelve strategies, three composition axes, and a fallback chain that only narrows

Reltio's strategy set is **crosswalk-centric**, which is the first structural difference from most home-grown engines. The twelve documented `survivorshipStrategy` literals are `LUD` (the default), `SRC_SYS`, `Frequency`, `Aggregation`, a record-values based source-priority family configured with `winnerSourceType` (whose advanced variant is named `RecordBase`), `OldestValue`, `MinValue`, `MaxValue`, `OtherAttributeWinnerCrosswalk`, `WinnerEntityCrosswalk`, `ValueBasedPriority`, plus user-defined **custom strategies** that extend a parent via `mainSourceType` and `parentStrategyURI` ([Survivorship Rules](https://docs.reltio.com/en/model/consolidate-data/design-survivorship-rules/survivorship-rules)). Six of those twelve — `LUD`, `SRC_SYS`, `OldestValue`, `Frequency`, `OtherAttributeWinnerCrosswalk`, `WinnerEntityCrosswalk` — select a **crosswalk** first and then take whatever values that crosswalk contributed; only `MinValue`, `MaxValue` and `ValueBasedPriority` select on the value itself. An engine that reasons only over values (recency-of-value, longest-string) is missing the platform's primary axis. Two further facts are worth pinning: **there is no "longest string" strategy anywhere in Reltio's documented set** — the Data Modeler page listing UI names (Recency, Frequency, Minimum value, Maximum value, Other Attribute Winner Crosswalk, Source Systems) does not include one ([Manage Survivorship rules in Data Modeler](https://docs.reltio.com/en/objectives/model-data/data-modeling-at-a-glance/data-modeling-operation/define-entity-types-and-attributes/configure-survivorship-groups-in-data-modeler/manage-survivorship-rules-in-data-modeler)) — and `ValueBasedPriority` is the one strategy that **deliberately produces no OV at all**: "If none of the attribute values match those in the list, all values will have their OV flag set to `false`" ([Value-Based Priority Survivorship Strategy](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/value-based-priority-survivorship-strategy)). Failing closed is a design choice, not a bug.

Composition happens on three stacked axes, and conflating them is a common under-specification. The first is **per-attribute override inside a group**: a survivorship group carries `"default": true` and a `mapping` array of `{attribute, survivorshipStrategy, …}` entries, and "If the survivorship strategy, for an attribute, is not defined in the non-default survivorship group, the survivorship strategy for the attribute is inherited from the default survivorship group" ([Survivorship groups](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/survivorship-groups)). Resolution order per attribute is therefore three-level: the role-scoped non-default group, then the default group, then `LUD`. The second axis is **role scoping** — non-default groups apply "for users with specific roles only," associated through Rulesets, "allowing different users to see different OV values based [on] their assigned roles" ([Survivorship Rules](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/survivorship-rules)). A single global default plus a flat per-field override table covers one axis of two. The third is **conditional selection by another attribute's value**, marketed as the "dependent survivorship rule" but implemented purely as a `filter` predicate on sibling rules in the same mapping — two rules for the same nested `Overview` attribute, one gated on `Type = "Episode"` with `sourcesUriOrder` A,B,C,D,E,Reltio,F and one gated on `Type = "Documentary"` with C,A,B,D,E,Reltio,F ([Dependent Survivorship Rule](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/dependent-survivorship-rule)). It is a usage pattern of `filter` + `sourcesUriOrder`, not a distinct strategy value. Note the note's own caveat: whether two `filter`-gated rules for the same attribute can both match, and which then wins, **is not stated on the page fetched** — do not assume.

Ordering is where most home-grown engines diverge most sharply, because chaining in Reltio is neither a scored vote nor plain first-match-wins. It is a **set-narrowing pipeline with an explicit trigger condition**: "If a strategy returns two or more winner values, its fallback strategy will use only the winner values and winner crosswalks from the strategy" ([Survivorship Rules](https://docs.reltio.com/en/model/consolidate-data/design-survivorship-rules/survivorship-rules)). The trigger is configurable via `fallbackUsingCriteria`: `MORE_THAN_ONE` (the default) fires only on multiple OVs, `ZERO` only when nothing survived, and `ZERO_OR_MORE_THAN_ONE` on either ([Configuring Fallback Strategies](https://docs.reltio.com/en/developer-resources/system-administration-apis/system-administration-apis-at-a-glance/configuration-api/configuring-fallback-strategies-for-survivorship-rules)). Mechanically: `winners = strategy₀(candidates)`, then for each fallback *i*, if `trigger(criteria, |winners|)` then `winners = strategyᵢ(winners)`. No rule contributes a partial score and a later rule can never resurrect a value an earlier one eliminated. Fallbacks also do not inherit — "Each Attribute must have its own set of Fallback Strategies defined separately" — and `fallbackStrategiesChain` was deprecated in favour of `fallbackStrategies` on 04/11/2017 ([Configuring Fallback Strategies](https://docs.reltio.com/en/developer-resources/system-administration-apis/system-administration-apis-at-a-glance/configuration-api/configuring-fallback-strategies-for-survivorship-rules)). Residual ties resolve under **two coexisting contracts**: non-advanced `LUD` takes "only the first crosswalk," while the opt-in `survivorshipAdvancedBehavior` array (supported for `LUD`, `OldestValue`, `SRC_SYS`, `RecordBase`) makes "all of those crosswalks become winners" ([Advanced Survivorship Strategies](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/advanced-survivorship-strategies)). The existence of `sortCrosswalksInSrcSYSNonAdvanced` — which sorts crosswalks by Type, SourceTable and Value — is the tell that Reltio hit the obvious bug: **"the first crosswalk" is meaningless without a total order**, and an engine relying on "first" with no defined sort key is non-deterministic across reloads.

The two mid-market vendors publish the same composition doctrine in plainer language, and Profisee's formulation of the cascade is the most directly reusable sentence in either corpus: "Most mature survivorship strategies combine multiple rule types based on need either by defining different rules per attribute or creating a cascading logic that allows the system to fall back on another rule should the preferred attribute not exist **or does not meet standards**" ([Profisee, MDM Survivorship](https://profisee.com/blog/mdm-survivorship/)). That clause names **two distinct fallback triggers** — absence and failing a quality standard — a stricter contract than a null-coalesce chain, and the only published hook for treating a suspect winner as a mid-survivorship quality problem. Profisee's six named rule types are **Source System Priority, Most Recent Update, Most Complete Record, Data Quality Score, Conditional Rules, Hybrid Approaches**, with a second Profisee article giving a looser, non-reconciling list (Recency rule, System prioritization rule, Minimum/maximum value signals, Aggregated data, Most complete data, Custom rules) that should be treated as informal ([Profisee, What Is a Golden Record?](https://profisee.com/blog/what-is-a-golden-record/)). Data Ladder publishes a business-level six — **Trusted source wins, Most complete wins, Most recent wins, Verified value wins, Most frequent wins, Conditional overwrite** ([Data Ladder, Guide to data survivorship](https://dataladder.com/guide-to-data-survivorship-how-to-build-the-golden-record/)) — and, separately, DataMatch Enterprise's actual mechanical options: **Longest, Shortest, Maximum, Minimum, Most Popular**, with the default that "the first record in a match group is automatically selected as the master record" ([Data Ladder, Best practices for using DataMatch Enterprise](https://dataladder.com/guide/best-practices-for-using-datamatch-enterprise/)). That default is an implicit, order-dependent rule and a silent-default hazard worth grepping for in any home-grown equivalent.

| Composition mechanism | Vendor name | What it actually does | General or dataset-specific |
|---|---|---|---|
| Per-attribute strategy override | `mapping` entries in a survivorship group (Reltio); "define rules at attribute level" (Profisee) | Three-level inheritance: role group → default group → `LUD` | **General** — structure, no corpus literals |
| Role-scoped rule sets | Survivorship groups + Rulesets (Reltio) | Different users see different OVs | **General** |
| Conditional rule selection | `filter` + `sourcesUriOrder` (Reltio); "Conditional Rules" (Profisee) | A sibling attribute's value picks the source order | **Dataset-specific by construction** — the filter literal (`"Episode"`) is a corpus value; legitimate when it encodes a business fact, illegitimate when it encodes an observed correlation |
| Fallback chain | `fallbackStrategies` + `fallbackUsingCriteria` (Reltio); "cascading logic" (Profisee) | Narrows the previous step's winner set; triggers on `ZERO` / `MORE_THAN_ONE` / both | **General** |
| Tie policy | `survivorshipAdvancedBehavior` (Reltio) | first-crosswalk-wins vs all-tied-win, per strategy | **General** — but must be *chosen*, not defaulted |
| Write guard | "Conditional overwrite" / "Overwrite to is empty" (Data Ladder) | Winner selection and permission-to-write are separate stages | **General** |

## Single-source, contested, and many-to-one are three different problems

Reltio treats the single-source case as a **pre-filter, not a fallback**, and states it verbatim: "If the strategy is applied to only one value, this value and its crosswalk become winners, irrespective of whether this crosswalk has a source from the priority list or not" ([Survivorship Rules](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/survivorship-rules)). This fires *before* strategy evaluation, which is why `SRC_SYS` with an unlisted source still yields an OV for a single-source attribute but yields **no OV at all** when several unlisted sources contest it: "If the business model does not specify source priorities and the priority list is also absent, no values are survived (all values have ov=false)" ([Survivorship Rules](https://docs.reltio.com/en/model/consolidate-data/design-survivorship-rules/survivorship-rules)). An implementation that runs source priority uniformly diverges from Reltio on exactly this class of attribute — Reltio keeps the value, naive priority drops it. The note flags one honest ambiguity here: whether the single-value short-circuit applies to **every** strategy or only to `SRC_SYS` "is not stated unambiguously," since the sentence appears within the `SRC_SYS` discussion but is phrased generically. The candidate set every strategy then runs over is all values minus end-dated crosswalks ("Crosswalks with end date (delete date): Do not participate in OV calculation just as those crosswalks do not exist"), minus ignored values, minus anything outside `sourcesForOv` ([Survivorship Rules](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/survivorship-rules)). `Aggregation` is the documented exception: "All presented values become winners (`ov` = True)."

The mid-market vendors are weaker here, and the report should not pretend otherwise: **neither Profisee nor Data Ladder gives a formal single-source case**. Both fold it into the overwrite mechanic — an uncontested value fills an empty target under "Conditional overwrite," gated by the literal predicate "Overwrite to is empty," whose stated purpose is that "Existing values must be protected" ([Data Ladder, Guide to data survivorship](https://dataladder.com/guide-to-data-survivorship-how-to-build-the-golden-record/)). Profisee instead reclassifies it out of survivorship altogether, calling it **enrichment**: "the customer email may exist alongside the name in the CRM, but the business locations and company name live in the ERP. Enrichment in MDM platforms brings these records together in a single, golden record" ([Profisee, What Is a Golden Record?](https://profisee.com/blog/what-is-a-golden-record/)). That vocabulary split is a usable audit axis on its own: **an implementation that runs contest logic over a single candidate is doing survivorship where enrichment was called for, and will report spurious "wins"** — inflating any metric that counts resolved conflicts. What neither vendor publishes is what happens to a single-source value when the target is already populated and the guard says "only when empty"; whether the incoming value is dropped, queued or recorded is unstated.

The many-source-fields-to-one-target-field case has **no crisp vendor term**, and the honest answer is a pair of them. Data Ladder names **cross-column matching** for comparing differently-named fields (Company Name to Organization, Email to Contact Info) — though that quote reached the researcher via Data Ladder site-search synthesis rather than a direct page fetch, so treat the example as indicative, not verbatim ([Data Ladder, dedupe software / multi-source integration](https://dataladder.com/dedupe-software-tools-for-multi-source-data-integration/)) — and **"Suggest Mapping,"** which "intelligently maps all fields" by "analyzing value distributions" ([Data Ladder, Best practices for using DataMatch Enterprise](https://dataladder.com/guide/best-practices-for-using-datamatch-enterprise/)). Around that sits **source-to-target mapping** as a governance artifact capturing "a set of decisions" about value interpretation, defaults and assumptions, with two named sub-concepts, **Code translation** and **Precedence logic**, and the instruction to "Treat mapping as a living artifact" — "If your mapping document is older than your last pipeline change, it's already wrong" ([Data Ladder, Source-to-Target Mapping](https://dataladder.com/source-to-target-mapping-best-practices/)). Data Ladder explicitly declines a dedicated name, handling structural differences under **Data Parsing**, "Structural Heterogeneity" and "Lexical Heterogeneity" and stating that "the process doesn't use a specific named concept—it's simply called data standardization and transformation" ([Data Ladder, Data Merging](https://dataladder.com/merging-data-from-multiple-sources/)). No vendor in scope uses "attribute consolidation" or "semantic alignment"; do not attribute those terms. The architectural point survives the terminological mush: **both vendors place semantic alignment upstream of survivorship**. A design that resolves `description` / `companyDescription` / `allDescriptions` *inside* its survivorship pass has collapsed two stages the vendors keep separate — and that collapse is precisely how a length-based tiebreak ends up substituting for a mapping decision.

Which brings the length question to a head. **"Most complete" is defined as raw character count in Data Ladder's product**, unambiguously: "Longest" "selects the master record with the highest number of characters in the chosen data field," "Shortest" the lowest ([Data Ladder, Best practices for using DataMatch Enterprise](https://dataladder.com/guide/best-practices-for-using-datamatch-enterprise/)), and the merging article states it outright — "Most Complete Wins – Non-null or longest value prevails" ([Data Ladder, Data Merging](https://dataladder.com/merging-data-from-multiple-sources/)) — with the canonical illustration itself a longer-is-better case, "Full company name replaces an abbreviation." Profisee's identically-named rule means something entirely different: "Most Complete Record" "favors the record with the fewest incomplete or empty attributes" — a **null count, not a character count** ([Profisee, MDM Survivorship](https://profisee.com/blog/mdm-survivorship/)). These are two different rules that must not be conflated in an evaluation. And the notable absence: **no vendor text in this scope warns that character count is a poor quality proxy.** The nearest thing is Profisee's caution that completeness rules applied independently carry a "high risk of error." Any argument that a concatenated junk value, a padded value, a duplicated clause or boilerplate will beat a correct terse value is therefore **this report's analysis, not vendor guidance** — accurate, but unsupported by the vendor corpus, and it should be presented that way in an audit.

## Provenance is the crosswalk, and losing values are retained by construction

Reltio's answer to "how is provenance of losing values retained" is that the question does not arise, because **nothing loses destructively**. "Crosswalks are analogous to the Primary Key or Unique Identifier in RDBMS," carrying `type`, `value`, `dataProvider`, `sourceTable` and `URL`, and "Reltio associates each supplied attribute with data provider crosswalks" ([Crosswalks](https://docs.reltio.com/en/objectives/model-data/data-modeling-at-a-glance/data-modeling-operation/define-crosswalks-for-data-sources/crosswalks)). Merge "aggregates what's called the crosswalks, and the attribute values, relationships, and interactions from all the contributing profiles, and then combines them into the winning, or golden, profile" ([Reltio match and merge](https://docs.reltio.com/en/reltio/what-does-reltio-do/what-reltio-does-at-a-glance/data-unification-and-mdm-at-a-glance/data-unification-and-mdm-in-detail/reltio-match-and-merge)). OV is a per-value boolean evaluated at read time — survivorship "operates separately from merging, executes in real-time during API calls" — and the read contract exposes both projections: "When `ovOnly` is absent or set to false, the system uses all mapped values, including values marked as `"ov":"true"` and `"ov":"false"`" ([Get Entity](https://docs.reltio.com/en/developer-resources/entity-management-apis/entity-management-apis-at-a-glance/entities-api/get-entity)). Streaming preserves an instructive asymmetry: "crosswalks are not filtered based on the OV status of their associated attributes, and a crosswalk may still appear in the crosswalks section even if all of its attributes have `ov: false`" ([Message streaming](https://docs.reltio.com/en/developer-resources/data-integration-apis/data-integration-apis-at-a-glance/events-api/message-streaming)).

**Survivorship is a view, not a write** — and that single decision is what buys role-scoped OV, replaying a rule change without re-merging, and lossless unmerge ("Reltio creates unique URIs for each entity before merging them. This enables you to unmerge them later if necessary," with the documented caveat that `matchBeforeCreate: true` forfeits it). Two refinements are easy to miss in a home-grown model with one `source_id` column. First, `dataProvider: false` separates **identity provenance from value provenance**: "Non-data providers are associated with an overall entity (or relationship). Supplied attributes will NOT be associated with this crosswalk" ([Crosswalks API](https://docs.reltio.com/en/developer-resources/entity-management-apis/entity-management-apis-at-a-glance/crosswalks-api)). Second, pinning and ignoring are out-of-band flags that pre-empt every strategy — "For a pinned value, survivorship rules are not applied… All pinned values become OVs, and all attribute's survivorship rules are just ignored," while ignored values "are not participating in OV calculation, just as those attributes don't exist" — **plus a documented conflict policy for the flags themselves**, `pinIgnoredPriority`, an array of `"ignored"`, `"pin"`, `"neutral"` defaulting to `["ignored", "pin", "neutral"]` where "The leftmost position indicates highest priority" ([Pinned or Ignored Attributes Merges](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/design-survivorship-rules/pinned-or-ignored-attributes-merges)). The worked example is the whole point: `Johnny` (Ignored) merged with `Johnny` (Pinned) survives as **ignored** under the default, and as **pinned** under `["pin", "ignored", "neutral"]`. Note also the *ordering* guarantee — pinned first, ignored last in the returned value list — which a boolean OV flag alone does not express. What Reltio's public docs do **not** contain is an "explain why this value won" endpoint; the note records that as absent, not as confirmed missing.

Against that, the mid-market vendors are a documented void, and the audit should not hold a home-grown engine to a bar these vendors never set. **No vendor in the Profisee/Data Ladder scope prescribes retaining losing attribute values with provenance.** Profisee's survivorship blog is silent; its solution page "focuses on selecting which information survives rather than managing rejected data" while claiming "Complete transparency into why records matched and how golden records were formed — so you can trust and audit every outcome," which is marketing, not a mechanism ([Profisee, Matching and Survivorship](https://profisee.com/solutions/initiatives/matching-and-survivorship/)). Data Ladder's only retention guidance is at *record* level — "Purging a list doesn't mean deleting it entirely" ([Data Ladder, Merge Purge Guide](https://dataladder.com/merge-purge-guide/)) — never at attribute level. The practitioner literature supplies the cheaper substitute that actually matters for an over-fitting audit: rule-based matching's output carries "the rule number used to generate that match," where ML carries only a confidence score ([insightful-data-lab](https://insightful-data-lab.com/2026/03/15/entity-resolution/)). **Rule-firing provenance is the audit instrument for reward hacking**: if one rule accounts for most matches on source pair A and near-zero on source pair B, that rule is fitted. That inference is this report's, drawn from the provenance property the source describes, not a published method. And the governing principle is stated plainly enough to quote in a design doc: "Which email survives a merge should be a rule, not an accident of ingestion sequence. Configure per attribute" ([logiciel.io](https://logiciel.io/blog/entity-resolution)); "Without explicit rules, your system either picks arbitrarily or fails the merge" ([Data Ladder, Data Merging](https://dataladder.com/merging-data-from-multiple-sources/)).

## What separates a general rule from one fitted to your two databases

This is the audit's load-bearing section, so the criterion goes first: **a general mechanism computes its constants from the corpus at runtime; a fitted one contains literals drawn from a particular corpus.** Every general mechanism found in the research has the first shape, and every anti-pattern has the second. The mechanical smell test needs no new data — grep the rule set for literals, and ask of each constant whether a *count over the corpus* would produce it.

### Parent/subsidiary versus genuine duplicate

The practitioner consensus is that this is **not a string-matching problem**. It is solved by modelling the relationship as a first-class typed edge distinct from a merge, and by resolving to an external identifier authority that publishes who owns whom. "Matching is not merging" — resolution is kept architecturally separate from survivorship ([insightful-data-lab](https://insightful-data-lab.com/2026/03/15/entity-resolution/)) — and the cost asymmetry mandates treating merge and split as "two separate decisions rather than one," because "A false split leaves one entity as two records… and is fixable later by merging. A false merge combines two entities into one, which propagates a wrong identity into every downstream consumer and is fixable only by reconstructing what was combined" ([logiciel.io](https://logiciel.io/blog/entity-resolution)). The authorities that maintain corporate hierarchy at scale define the relation by **legal/financial consolidation, never name similarity**: GLEIF's LEI Level 2 has entities report their direct and ultimate **accounting consolidating parent**, an accounting-standard test rather than an ownership-percentage or name test, published as RR-CDF (v2.1, May 2021) with a separate **Reporting Exceptions** format for entities that legitimately report no parent ([GLEIF, Level 2 Data: Who Owns Whom](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-2-data-who-owns-whom), [RR-CDF 2.1](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-2-data-relationship-record-rr-cdf-2-1-format)). D&B's patent enumerates **eight business classifications** (single-location subsidiary, headquarters, branch, division, subsidiary, parent, domestic ultimate, global ultimate) and **two linkage relation types** (branch→headquarters, subsidiary→parent), noting that other family relationships exist but go unlinked "because the affiliated company has no legal obligation for the debts of the other company" ([US Patent 8,036,907](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8036907) — from a search excerpt of the patent text, not the primary filing read directly). The vendor pattern is to **buy the hierarchy, not derive it from names**: Reltio ships D&B enrichment that materialises hierarchies onto profiles ([Reltio, Hierarchies and Relationships](https://docs.reltio.com/en/applications/data-integrations/data-enrichment-integrations-at-a-glance/reltio-enrichment-with-db-at-a-glance/reltio-enrichment-with-db-set-up/working-with-reltio-enrichment-with-db/enriching-profiles/hierarchies-and-relationships)), and Informatica's Hierarchy Manager models typed relationships among entities — though **both Informatica pages returned HTTP 403 to the researcher and are quoted from search excerpts only** ([Hierarchy Manager](https://docs.informatica.com/master-data-management/multidomain-mdm/10-3/data-steward-guide/using-the-hierarchy-manager/hierarchy-manager-functionality.html)). No Profisee hierarchy documentation was retrieved at all.

On the hardcoded suffix list specifically, the sources split — and the split resolves cleanly by asking *where the list sits*. As **normalization before comparison** it has statutory precedent (UK Companies House name matching "automatically excludes legal suffixes like Ltd, Limited, PLC, and LLP" — via a secondary source restating the rules, not the Companies House site itself, [Companies House name matching rules](https://mycompanyregistration.uk/blogs/our-ultimate-guides/what-are-companies-house-name-matching-rules-in-the-uk)) and vendor endorsement ("Legal suffixes like Inc., Corp., LLC, Ltd., GmbH, and S.A. serve legal purposes but add noise… For most operational uses, they should be stripped" — [Openprise](https://www.openprisetech.com/blog/company-name-normalization-rules-and-best-practices), which nonetheless requires a hand-maintained exception list for cases like "The Limited"). As the **discriminator between a duplicate and a subsidiary** it is an anti-pattern, and the one source that tests that use head-on shows the ordering is not merely incomplete but **inverted**: standard matchers score **"Acme Group Ltd" vs "Beta Group Ltd"** (different companies, should reject) *higher* than **"Acme Group Ltd" vs "Acme Holdings Ltd"** (plausibly the same entity, should accept), so "Lower the threshold to catch pair B and you also accept pair A as a false positive." Normalization "does nothing for common business-language tokens like Group, Holdings, International, Services and Solutions," which appear in **5–25% of records** and are sometimes discriminative and sometimes not — "a Solutions subsidiary is different from an Industries subsidiary." The recommended fix is not a longer list but **data-derived token weighting**, `weight(token) = log(N / count(token))` (IDF), which "automatically derives domain-specific token importance from your actual dataset, eliminating reliance on manual rule maintenance" ([Tilores](https://tilores.io/content/company-name-normalization-isnt-enough-for-fuzzy-matching/)). That sentence is the report's general-versus-fitted criterion in the vendor's own words.

Reltio's own published mechanisms for this problem are **generic rather than hierarchy-aware**, and the researcher found **no published Reltio mechanism that reasons about a parent/subsidiary relationship specifically** — no relationship-aware match operator, no documented "is-a-child-of suppresses match" feature. What exists is the **negative rule**, which "allows you to prevent any other rule from merging records" and, when true, "will demote any directive of merge coming from another match group to queue for review," with a negation-specific operand vocabulary (`notExactSame`, `notFuzzySame`, `or`, `and`, `equals`, `notEquals`, `nullValues`; the `not` operand is explicitly unsupported) and the constraint that "A match group can contain either a rule OR a negative rule, not both" ([Negative Rule](https://docs.reltio.com/en/reltio/what-does-reltio-do/what-reltio-does-at-a-glance/data-unification-and-mdm-at-a-glance/data-unification-and-mdm-in-detail/reltio-match-and-merge/match-group-elements---description-and-configuration/negative-rule)). The veto is deliberately **non-destructive**: demote to review, not suppress — which makes a home-grown "never match" list a *stronger and more dangerous* primitive, because it removes the pair from human sight. The steward **not-a-match flag** is the true suppress-this-known-non-match primitive, and its documented reset behaviour matters: entities can be "removed from the not-a-match list to ensure such entities can participate in matching," so it is not a permanent blacklist by default ([Reset the as-Match Not-a-Match Flag](https://docs.reltio.com/en/explore/get-a-crash-course/get-ready-to-turn-your-data-into-action/learn-about-multidomain-mdm/reltio-match-merge-and-survivorship/match-group-elements---description-and-configuration/reset-the-as-match-not-a-match-flag)). One claim must be explicitly **not** reported as Reltio guidance: a web-search result asserted that for parent-subsidiary scenarios "you would typically configure a negative rule that detects the parent-subsidiary relationship and prevents these entities from being merged." That was **search-engine-generated inference, not a quote from any Reltio page**, and no retrieved Reltio page states it.

### Blocking and tokenization key selection

Tokenization **is** blocking in Reltio, and the blocking key is a **token phrase**, not a token: tokens are cross-multiplied across attributes, and "Any other profile containing this identical phrase becomes a match candidate" (example `<elizabeth:smith>`), with phrase count equal to `[all values for attribute 1] × … × [all values for attribute n]` ([Match Token Generation](https://docs.reltio.com/en/reltio/what-does-reltio-do/what-reltio-does-at-a-glance/data-unification-and-mdm-at-a-glance/data-unification-and-mdm-in-detail/reltio-match-and-merge/match-group-elements---description-and-configuration/rule-element/match-token-class/match-token-generation), [Design your Match Tokenization Scheme](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/configure-match-rules-overview/create-initial-match-rules/design-your-match-tokenization-scheme)). Fifteen token classes are published in `com.reltio.match.token.*`, each with a defined token budget: `ExactMatchToken` and `ExactNumberMatchToken` and `SoundexTextMatchToken` and `AddressLineMatchToken` emit 1; `DoubleMetaphoneMatchToken`, `DictionaryStatsPhoneticFuzzyToken` and `ComplexPhoneticNameToken` up to 2; `FuzzyTextMatchToken` up to 6; `OrganizationNameMatchToken` and `BasicTokenizedOrganizationNameMatchToken` one per non-noise word plus pairwise combinations; `RangeNumericMatchToken` and `VolumeMatchToken` parameterised numerics; `CustomMatchToken` a container; and `DistinctWordsMatchToken` **up to 1,000 tokens per value at a default 50% threshold** ([Match Token Classes](https://docs.reltio.com/en/reltio/what-does-reltio-do/what-reltio-does-at-a-glance/data-unification-and-mdm-at-a-glance/data-unification-and-mdm-in-detail/reltio-match-and-merge/match-group-elements---description-and-configuration/rule-element/match-token-class/match-token-classes)). The name `SoundexTextExactMatchToken` appears on the generation page but not in the class table — treat it as unconfirmed, possibly a doc error.

Three Reltio facts bear directly on auditing a home-grown blocker. First, **token/comparator alignment is the central correctness rule**: pairing "a comparator class and matchToken class that are aligned" prevents cases "where tokens attract candidates that the comparator logic then rejects," and across all five published example configurations **exactly one pattern is universal** — a fuzzily-compared attribute is either tokenized with the same algorithm family or placed in `ignoreInToken` with blocking carried entirely by a different exact attribute. Never is a fuzzily-compared attribute blocked on exactly. Second, **blocking is opt-out, not opt-in**: `ignoreInToken` exists to "prevent default class assignment," which is the reverse of most hand-built matchers, and the scheme-design method ends by applying it "to all remaining attributes." Third, there is a **hard cap of 300 profiles per token phrase** — "The system caps candidates per token phrase at 300 profiles to prevent performance degradation" — a **silent recall cliff**: any block wider than 300 truncates, and pairs are dropped without any rule evaluating false. That is directly relevant to a matcher reporting zero uncompared pairs; Reltio's own engine would not make that claim. Key-selection guidance is a cardinality heuristic, stated with an example: "State might be a decent element in a match rule for your comparison tactic, but a poor attribute for tokenization because it only has 26 unique values," and the trade-off is resolved with an explicit preference — "most agree that it is more important from a performance perspective to reduce the number of token phrases, even at the expense of increasing the number of match candidate pairs returned" ([Design your Comparison Formulas](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/configure-match-rules-overview/create-initial-match-rules/design-your-comparison-formulas)).

The literature supplies two dataset-independent replacements for a hand-picked key. **Schema-agnostic (token) blocking** "creates blocks by using parts of any attribute value in each entity as signatures, rather than relying on predefined schema knowledge. This approach requires only the raw entity profiles themselves as input — no domain expertise or structural metadata" ([arXiv 2204.08801](https://arxiv.org/html/2204.08801)); all entities sharing a token land in the same block, attribute names and boundaries ignored entirely ([Papadakis et al., VLDB vol. 9](https://doi.org/10.14778/2856318.2856326) — **search excerpt only; the PDF fetch failed with ECONNRESET and no numbers were read**). Its measured cost is the number to carry into the audit: recall "almost perfect… significantly exceeds 90%" but "precision is consistently quite low, as its highest value is lower than **0.003**," with F1 "far below 0.1 across all datasets," repaired by **meta-blocking** in two dataset-independent stages — co-occurrence weighting ("the more blocks they share and the more distinctive (i.e., infrequent) the corresponding signatures are, the more likely they are to match") and edge pruning by weight threshold or top-K cardinality ([arXiv 2204.08801](https://arxiv.org/html/2204.08801)). **Unsupervised blocking-key selection** is the other: "The harmonic mean of discriminability and coverage is computed for all valid attributes, with the one having the maximum score selected for defining blocking keys" ([Springer, 2015](https://link.springer.com/content/pdf/10.1007/978-3-319-18032-8_45.pdf)), later generalised to multi-criterion selection over "key coverage, block sizes, and blocks distribution" ([Information Sciences](https://www.sciencedirect.com/science/article/abs/pii/S0020025525010898)), and also cast as Fisher feature selection ([QUB](https://pureadmin.qub.ac.uk/ws/files/175528318/An_Unsupervised_Blocking_Technique_For_More_Efficient_RL.pdf)). The exact discriminability and coverage formulas were **not retrieved** — only the fact that their harmonic mean is the criterion. And the configurability answer comes from Splink: **a union of 3–10 measured rules, not one chosen key** — "specify multiple blocking rules such that it becomes highly implausible that a true match would not meet at least one of these blocking criteria… Generally between about 3 and 10 rules are recommended" ([Splink, What are Blocking Rules?](https://moj-analytical-services.github.io/splink/topic_guides/blocking/blocking_rules.html)) — with `count_comparisons_from_blocking_rule()` reporting the pair count a candidate rule generates, and the workflow being to start strict and "incrementally loosen them to see the impact on runtime and quality" ([Splink, Blocking Rule Performance](https://moj-analytical-services.github.io/splink/topic_guides/blocking/performance.html)). Keys are **parameters with measurable cost, not code**; a system with one hardcoded key has no such dial.

### Relationship-edge derivation

There is a mature, purely data-driven chain here, and it needs **only column values** — which is exactly the input a pair of flat PostgreSQL sources with no declared foreign keys provides. Discover **inclusion dependencies**, where `R ⊆ S` holds when "for every tuple in R there exists a tuple in S where the values match," used "primarily… in foreign key discovery, which aims to suggest possible joins over tables"; crucially, IND discovery "operates directly on raw data… without requiring pre-declared database constraints," motivated precisely by constraints being "lost during data export, or to not have been defined in the first place" ([Desbordante, arXiv 2608.02213v1](https://arxiv.org/html/2608.02213v1)). SPIDER tests all attribute pairs in parallel via a disk-based sort-merge join ([Bauckmann & Leser](https://hpi.de/oldsite/fileadmin/user_upload/fachgebiete/naumann/publications/PDFs/2007_bauckmann_efficiently.pdf) — search excerpt, PDF not text-extracted); BINDER handles unary and n-ary INDs and is "up to **26x faster than Spider** and more than **2500x faster than Mind**" ([PVLDB](https://dl.acm.org/doi/10.14778/2752939.2752946)); FAIDA "guarantees completeness but permits false positives" with a reported small false-positive rate. Then **classify INDs as foreign keys** with structural features — Rostin et al. used column-name similarity, value coverage and dependent-vs-referenced ratios, value typicality, relative table sizes and out-of-range detection, cross-validated on "six different databases from different domains" with "four different classification methods," reporting "roughly identical precision and recall… only **5% on average for J48**" ([WebDB 2009](https://hpi.de/fileadmin/user_upload/fachgebiete/naumann/publications/PDFs/2009_rostin_a.pdf) — **feature families confirmed but exact formulas not extracted, and the precision/recall relation reached the researcher via search excerpt; absolute values were not obtained**). HoPF and the CEUR FK-identification paper were **not readable** (auth redirect and unread PDF respectively), so no cross-approach comparison is supportable.

Junction-table detection is the weak link, and it has a documented failure mode filed as a bug. The structural definition in circulation is that junction tables are "non-prime tables whose primary key columns are foreign keys" ([DZone](https://dzone.com/articles/using-junction-or-associative-tables-in-entity-fra)), and tooling implements automatic detection ([JetBrains](https://www.jetbrains.com/help/idea/jpa-buddy-reverse-engineering.html)). But `drizzle-kit pull` "treats domain tables with exactly two foreign keys as junction tables," and the bug report states the general principle: "the presence of exactly two foreign keys is not enough to establish that a table is a junction, as a domain entity can legitimately reference exactly two other tables. Primary keys, unique constraints, non-FK columns, and the general table structure need to be considered," concluding that "generating the direct foreign-key relations unconditionally would be safer than replacing them with an inferred through-relation" ([drizzle-orm #6253](https://github.com/drizzle-team/drizzle-orm/issues/6253)). The discriminating signal practitioners use is a **composite primary key of exactly the two FKs**; the moment a table accrues a surrogate id, timestamps, payload columns or a unique-together constraint instead of a composite PK, it is a domain entity. **No junction-detection heuristic with published precision or recall was found anywhere in the research** — the only quantified figures in this whole area are BINDER's speedups and Rostin's precision≈recall-within-5% statement. The honest general chain is therefore: PostgreSQL catalogue (PK/unique only) → IND discovery on values → Rostin-style structural features → FK candidate scores → **junction detection as a report, not a silent rewrite**. A system that instead consults a list of known table names is doing at step one what the literature does at step three, and will not transfer. One open question flagged rather than resolved: the researcher found **no source on IND discovery across two independent databases** as opposed to within one schema, and cross-source INDs are a weaker signal — overlapping values across two systems may indicate a shared code list rather than a reference.

## Documented anti-patterns, and the one the literature does not cover

The most directly relevant published warning is not about ML overfitting at all. It is that **optimising a metric that only counts duplicates found systematically drives a system toward over-merging**: "A program measured on duplicates alone will push toward over-merging, because duplicates are easy to count from the output while wrong merges are not" ([insightful-data-lab](https://insightful-data-lab.com/2026/03/15/entity-resolution/)). That is the precise mechanism of reward hacking in an ER system — the good outcome is visible in the output and the bad one is not — and the cost asymmetry makes it expensive rather than merely inaccurate. Compounding it, **the F-measure is not a safe optimisation target**: Hand and Christen show it "can be expressed as a weighted sum of precision and recall, with weights which depend on the linkage method being used," so the weight given to recall "depends upon the outcome of the evaluated classification method," when "the relative importance assigned to precision and recall should be an aspect of the problem and the researcher or user, but not of the particular linkage method being used" ([Statistics and Computing, 2018](https://link.springer.com/article/10.1007/s11222-017-9746-6)). A rule set tuned until F rose cannot be defended by that F. Two labelled-set pathologies compound further: the class imbalance is structural — "1000 entities can create almost 2 million negative examples" — and random negative sampling is the trap, because "the selected samples are not likely to cover the most challenging training samples given the nature of entity resolution" ([arXiv 1509.06659](https://arxiv.org/pdf/1509.06659)).

The eight anti-patterns the research traces to a source, each with its tell: **scoring on duplicates found** (tell: the reported metric has no false-merge term); **a single threshold for both merge and split**, contradicting the cost asymmetry (tell: one number governs both); **comparing rule sets by F-measure** (tell: "we tuned until F went up"); **a hardcoded keyword or suffix list as the duplicate-versus-subsidiary discriminator** (tell: the list names tokens that happen to occur in *this* corpus — swap the corpus and it is silent, whereas `log(N/count(token))` re-derives itself); **"exactly two FKs ⇒ junction table"**; **a hand-picked blocking key with suspiciously high candidate precision**, against a general baseline of precision below 0.003 at >90% recall (tell: a key generating few, mostly-correct candidates was almost certainly chosen with knowledge of the answers); **random negative sampling** for rule validation; and **tuning blocking against match quality on the labelled set**, which is why Splink deliberately separates model-training blocking rules from prediction blocking rules — training rules exist "to reduce the runtime of model training by choosing training rules that reduce the number of record pairs in the training set," a different objective from prediction quality ([Splink, Model Training Blocking Rules](https://moj-analytical-services.github.io/splink/topic_guides/blocking/model_training.html)). Blocking choices are to be justified by a **measured pair count, not by outcome quality on the labelled set**.

Three honest caveats belong with that catalogue. First, **no paper specifically on over-fitting hand-written ER rules to a single ground-truth dataset was found**. The formal literature covers overfitting of *learned* models and flaws in *metrics*; the hand-tuned-rules case is served only by practitioner writing (logiciel.io, insightful-data-lab, Tilores) and by tool-design choices in Splink. This specific worry is under-served by the literature, and the audit should not pretend to cite a standard that does not exist. Second, **neither Profisee nor Data Ladder warns about hardcoding rules per dataset or over-fitting to sample data** — checked across Profisee's survivorship blog, Data Ladder's survivorship guide, its DataMatch best-practices guide and its definitive matching guide; all four are silent, with the best-practices page in particular focused "on positive recommendations rather than cautionary advice." Report that as a gap in vendor literature, not as vendor endorsement. What the vendors *do* warn about is worth keeping: against record-level source trust — "Building logic that trusts full records from a single data source like 'trust the ERP for all customer data' can quickly lead to problems. Instead, build logic based on each attribute needed for a record" ([Profisee, MDM Survivorship](https://profisee.com/blog/mdm-survivorship/)); against recency without reliable cross-system timestamps; against completeness applied alone ("high risk of error"); and against blind overwriting — "you may end up overwriting valuable data with empty values" ([Data Ladder, Guide to data survivorship](https://dataladder.com/guide-to-data-survivorship-how-to-build-the-golden-record/)). Third, **Reltio publishes no quantitative acceptance metric at all** — no target precision, no recall estimate, no ground-truth construction guidance. Its documented workflow is a ~10% source-proportional random sample loaded with matching disabled, then iterate rebuild → review → hunt **false positives** → tighten, targeting fewer than 10 rules and "Five to seven is a good target," ordered "exact matches then moving on to a blend of exact and fuzzy, then moving on to heavily fuzzy," with success defined as "good enough for my business objectives" and the concession that "matching is always an approximation and will never be perfect" ([Testing and Tuning your Match Rule Design](https://docs.reltio.com/en/objectives/resolve-potential-matches/potential-matching-at-a-glance/potential-matching-navigation/configure-match-rules-overview/create-initial-match-rules/testing-and-tuning-your-match-rule-design)). The loop is **asymmetric on purpose**: recall is added deliberately by adding looser *rules*, while precision is defended by inspection. A home-grown matcher with an independent scorer and real ground truth is measuring something Reltio's own documented workflow does not.

## Conclusion

The audit question has a sharper answer than "look for hardcoded values." Every general mechanism in this corpus shares one shape — **it replaces a constant with a count over the corpus**, and produces that constant at runtime: IDF for token importance, discriminability × coverage for blocking keys, co-occurrence weights for meta-blocking, inclusion dependencies for relationship edges, crosswalk counts for `Frequency`, crosswalk dates for `LUD`. A fix that hardcodes what one of those would compute is fitted by definition, regardless of how well it scores. The corollary that should reorder the audit's priorities is that **high candidate precision from a hand-picked blocking key is evidence against the key, not for it**: the general baseline is precision below 0.003, and a general pipeline *expects* garbage-heavy candidate sets and prunes them statistically. So does the observation that the platform whose survivorship semantics are richest has **no longest-string strategy at all**, while the only vendor that ships one defines it as raw character count and publishes no caveat — meaning a length-based tiebreak inherits every failure mode of Data Ladder's "Longest" with none of the literature's cover.

Two structural recommendations follow that no amount of rule tuning substitutes for. First, **the decisive test is a held-out source pair, not held-out rows**: row-level holdout from the same two databases cannot detect a rule keyed to those databases' vocabulary, table names or value conventions, because the rule sees the same vocabulary in both splits — only a third source reveals it. This follows directly from schema-agnostic blocking's stated motivation of working without schema knowledge; a rule that needs the schema fails the source swap and nothing else exposes it. Pair that with rule-firing provenance: if one rule accounts for most matches on pair A and near-zero on pair B, that rule is fitted. Second, **stop resolving what should be declined**. With only two flat sources and no external identifier authority, no system can honestly claim to *distinguish* a subsidiary from a duplicate; the general, defensible move is to decline the merge and emit a typed "related / possible-hierarchy" edge for review — which is what the cost asymmetry demands anyway, since a false split is recoverable by merging and a false merge is recoverable only by reconstructing what was combined. Reltio arrived at the same conservatism by a different route: its veto demotes to review rather than suppressing, and its OV is a computed view over retained crosswalks rather than a destructive write, so a wrong rule is a wrong *read* and can be fixed by changing the rule. A home-grown engine that resolves survivorship destructively at merge time cannot replay a rule change, cannot scope OV by role, and cannot unmerge losslessly — which means every fitted rule it contains is baked into data rather than into configuration, and the audit is repairing history rather than a config file.
